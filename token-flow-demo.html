🔑 Cấu Trúc Token Lý Thuyết (JWT-like)

Token là một chuỗi chứa thông tin định danh và chữ ký số để đảm bảo không thể giả mạo. Dưới đây là minh hoạ token mẫu (JWT 3 phần):

TOKEN MẪU: header . payload . signature
// Header: Thuật toán mã hoá { "alg": "HS256", "typ": "JWT" } // Payload: Dữ liệu định danh người dùng { "userId": 42, "username": "vietphuc", "role": "BIDDER" } // Signature: HMAC-SHA256(base64(header) + "." + base64(payload), SECRET_KEY) // → Đảm bảo token không thể bị sửa đổi
📤 Cách Gửi Token Khi Đặt Giá — Chi Tiết
Bước 1 — Client Lưu Token Sau Login
// AuthService trả về token cho client String token = authService.login(username, password); // Client lưu token vào session ClientSession.setAuthToken(token); // ← Phải lưu token, hiện tại KHÔNG có!
Bước 2 — Gửi Token Kèm Khi Đặt Giá

✅ CÓ Token — An toàn

// BidClient gửi token + bid data Map payload = Map.of( "auctionId", auctionId, "amount", amount, "token", ClientSession.getAuthToken() // ← GỬI TOKEN );

❌ KHÔNG Token — Hiện tại

// BidClient gửi bidderId trần — giả mạo được! Map payload = Map.of( "auctionId", auctionId, "bidderId", "42", // ← Ai cũng ghi được số 42 "amount", amount );
Bước 3 — Server Xác Thực Token Trước Khi Xử Lý
// 1. Lấy token từ request String token = getRequiredText(request, "token"); // 2. Xác thực token → lấy userId thật User user = authService.authenticate(token); // 3. Chỉ dùng userId từ token — KHÔNG tin bidderId từ request! if (!(user instanceof Bidder bidder)) throw new AuthenticationException("Khong phai bidder"); // 4. Đặt giá — xác thực rồi mới cho qua BidTransaction bid = bidService.placeBid(auctionId, bidder, amount);

⚖️ So Sánh: Có Token vs. Không Token
Tiêu chí ❌ Hiện tại (Không token) ✅ Có token
Xác thực danh tính Không — Dùng bidderId từ request Có — verify token → lấy userId thật
Giả mạo request Dễ dàng — Ai cũng gửi được bidderId=42 Không thể — Cần token hợp lệ
Replay attack Có — Bắt request rồi gửi lại Giảm — Token có hạn, nonce/expiry
Phiên đăng nhập Không quản lý — Bidder tự do đặt Có — Token gắn với session
Logout vô hiệu hoá Không — Dùng thoải mái Có — Xoá token khỏi store
Ban user Không ngăn ngay Ngăn ngay lập tức — authenticate kiểm tra BANNED
📝 Code JWT Thực Tế Đã Triển Khai

1. JwtUtil.java — Tạo & Verify JWT

public final class JwtUtil { private static final SecretKey SECRET_KEY = Keys.hmacShaKeyFor(SECRET.getBytes(StandardCharsets.UTF_8)); private static final long EXPIRATION_MS = 120 * 60 * 1000; // Tạo JWT với HMAC-SHA256 public static String generateToken(int userId, String username, String role) { return Jwts.builder() .subject(String.valueOf(userId)) .claim("username", username) .claim("role", role) .issuedAt(new Date()) .expiration(new Date(System.currentTimeMillis() + EXPIRATION_MS)) .signWith(SECRET_KEY) .compact(); } // Verify chữ ký số — trả về null nếu không hợp lệ public static Claims validateToken(String token) { try { return Jwts.parser() .verifyWith(SECRET_KEY) .build() .parseSignedClaims(token) .getPayload(); } catch (JwtException e) { return null; // Token giả mạo! } } }

2. AuthService.java — Dùng JWT thay TOKEN_STORE

// AuthService KHÔNG còn TOKEN_STORE nữa! // JWT là stateless — server chỉ verify chữ ký public String login(String username, String password) { User user = userDAO.findByUsername(username).orElseThrow(...); // ... verify password ... return JwtUtil.generateToken( user.getId(), user.getUsername(), user.getRole()); } public User authenticate(String token) { int userId = JwtUtil.getUserIdFromToken(token); if (userId <= 0) throw new AuthenticationException(...); User user = userDAO.findById(userId).orElseThrow(...); if (user.getStatus() == BANNED) throw new ...; return user; }
✅ Đã Triển Khai JWT Thực Tế! Luồng mới:
Client

1. AuthClient.login() → Lưu JWT

Server trả về JWT token. AuthClient gọi ClientSession.setAuthToken(jwt) để lưu.

Client → Server

2. BidClient.placeBid() → Gửi JWT kèm

Client gửi { "token": "eyJhbGciOi...", "auctionId": "5", "amount": 150000 }

Server

3. RequestHandler → Xác thực JWT

authService.authenticate(token) → JwtUtil.validateToken(token) → verify chữ ký HMAC-SHA256 → lấy userId thật

Server

4. Chỉ dùng userId từ JWT — Không tin request

Dù hacker sửa bidderId trong request, server vẫn dùng userId từ JWT token đã ký.

🔐 Nguyên tắc cốt lõi:

"Không bao giờ tin bidderId từ request — chỉ tin userId từ token đã xác thực"
Token là bằng chứng người dùng đã đăng nhập. Server verify token → lấy userId thật → kiểm tra userId đó có quyền đặt giá không. Nhờ vậy, dù hacker có sửa bidderId thành 999, server vẫn chỉ dùng userId trong token (42).

🎯 Kết Luận

Hiện tại — Rủi ro

  • ❌ bidderId là plaintext — không xác thực
  • ❌ Ai cũng có thể giả mạo ID
  • ❌ Không có kiểm tra quyền sở hữu request
  • ❌ Token sinh ra nhưng không được dùng

Cần triển khai — An toàn

  • ✅ ClientSession lưu token sau login
  • ✅ Mọi request quan trọng gửi kèm token
  • ✅ Server verify token → lấy userId thật
  • ✅ Từ chối nếu token hết hạn/bị ban

🛡️ Token = "Chứng minh thư" số của request. Không có token, server không thể tin ai đang gửi request thực sự!
